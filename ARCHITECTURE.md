# Архитектура 2.1-dev

## Сохранённая основа
Java/XML/Material 3, Android API 24+, applicationId com.example.gymnotes, база fitpulse_database, существующие Firebase Authentication и Realtime Database, Яндекс MapKit. Firebase используется для аккаунта/заметок и дополнительных каталогов. Тренировки и завершения находятся в Room. Firestore, Storage и облачная синхронизация тренировок не подтверждены и не добавлены.

## Реализовано
DatabaseProvider — единый экземпляр Room; версия 7, явная миграция 6→7. Добавляет session_drafts, warmup DEFAULT 0 в completed_exercises и nullable source_session с уникальным индексом в completed_workouts. UUID сессии защищает от повторного завершения и восстановления старого черновика после завершения. Не удаляет и не пересчитывает историю. Неподдерживаемые версии не стираются автоматически.

SessionRepository — последовательная очередь локальных операций и транзакция завершения. SessionSnapshot — JSON-снимок упражнения и каждого подхода, независимый от изменений шаблона. Ключ черновика: (Firebase UID, workoutId). Запись при изменении, уходе с экрана и периодически для таймера. При завершении запись истории/подходов и удаление черновика происходят атомарно; повторное завершение отсутствующего черновика не добавляет дубликат. Шаблон с активным черновиком нельзя удалить.

DashboardViewModel + LiveData Room — обновление dashboard и объяснения прогресса. MainNavigation связывает существующие Activity; это постепенный переход, не полная миграция всех экранов на MVVM/Fragments. ViewBinding включён, новые generated bindings доступны; массовая конвертация legacy UI не сделана.

Объём = сумма weight × reps для отмеченных подходов, включая разминку. Число упражнений = число записей упражнений хотя бы с одним отмеченным подходом. Продолжительность округляется вверх до минут для совместимости существующей схемы. PR/сравнение рабочих весов исключает разминку. Имена упражнений пока служат legacy-идентичностью; одинаковые названия могут обозначать разную технику/оборудование — интерфейс предупреждает. Старые результаты 2.0 не считаются доказанными фактическими подходами.

## Ограничения и следующие шаги
Сохранение асинхронно: принудительное завершение процесса до фиксации транзакции может потерять самое последнее изменение. Требуются стресс-тесты и явный индикатор dirty/saved/error. Таймер восстановится по системному времени; изменение часов пользователем может исказить длительность. Нужен отдельный монотонный/boot-aware clock.

Пока нет синхронизации тренировок. План: стабильные UUID сущностей, per-user outbox в Room, WorkManager с сетью, версионированные операции по отдельным сущностям, серверные revisions, tombstones, идемпотентность operationId. Конкурирующие правки не заменяют весь документ: сохранять обе версии и показывать разрешение конфликта; завершённые сессии делать append-only с явными исправлениями. Firebase Rules и emulator tests должны предшествовать включению sync. Не использовать общий last-write-wins снимок всей базы.

Структура Coach Platform и подписок — будущий этап, не клиентская имитация серверного доступа. Платежи не подключены.
